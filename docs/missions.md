## 지금 코드와 맞춰 읽기

- **"구간"은 이미 있다.** 날 단위 개편(PR #53)으로 하루는 `CO.ENC_DAY`(4)번의 마주침이 됐고, 메모가 말한 "구간"이 이 마주침이다. 엔진은 이제 마주침을 "구간"이라 부르고 구간마다 사건 하나를 뽑는다.
- **층마다 시간 비용과 현장 구간 수도 이미 따로다.** 시간 비용은 `CO.TRIP_DAYS`(1 · 2 · 3 · 4 · 5일, 달력의 날), 현장 구간은 날 × `ENC_DAY`(1층 4 … 5층 20). 메모의 "1층 1턴 = 구간 5" 표는 이 숫자로 읽는다.
- **1층 짐이 차서 돌아오는 것도 이미 있다.** 층마다 `LOOT_SLOT`(4 · 2.2 · 1.5 · 1.25 · 1.2칸)이라 1층 하루 탐사의 짐이 13/17칸쯤 찬다. 채집품으로 옮길 때 이 숫자를 그대로 쓴다.
- 엔진 쪽 이름: 메모의 `w`(몬스터 무게) → `TripCfg.evs: Ev[]`(`{ k: 'fight', j, w }`). 지정 탐사의 무게(`DEX.TARGET_W`)도 여기로 들어간다. `Day.mon` → `Day.ev`는 채집 지점이 생기는 2단계에서 바꾼다(그때 저장 버전도 올린다).

## 한 줄 요약

우리 조의 탐사를 **다키스트 던전 형식의 구간 진행** 위에 **몬스터 헌터식 탐사**로 바꾼다. 한 구간에 사건 하나(채집 지점 · 조우 · 흔적)를 만나고, 조마다 정하는 **임무**(채집 · 사냥 · 탐색)가 그 사건들의 비중을 바꾼다.

## 왜

- **초반이 단조롭다.** 첫 두 달은 1층만 열려 모든 조가 같은 층을 같은 방식으로 다닌다. 임무가 있으면 같은 1층에서도 "지금 벌 조 · 지도를 그릴 조 · 몬스터를 연구할 조"가 갈린다.
- **조직의 모양이 결정에서 생기게 한다.** 채집 위주면 물량형, 사냥 위주면 소재 · 도감형, 탐색 위주면 개척 · 정보형. 유형을 고르게 하지 않고, 조마다 정한 임무가 쌓여 모양이 된다.
- **조별 정보가 많아도 읽을 것은 하나로.** 임무마다 귀환 보고의 초점이 다르다(채집: 짐 · 시세 / 사냥: 도감 · 소재 / 탐색: 지도 · 발견).
- **직업과 시너지에 쓰임이 생긴다.** "이 조에는 이 임무"라는 짝이 생긴다.
- **채집과 사냥이 섞여 있다.** 지금은 전리품(가죽 · 점액 · 마석)도 싸움에서 나와서, 환경에서 얻는 것과 몬스터에게서 얻는 것이 구분되지 않는다.

## 핵심 개념

| 구분 | 무엇에서 얻나 | 몬헌의 대응 |
|---|---|---|
| 채집 | 환경 (약초밭 · 광맥 · 결정 군락) | 채집 포인트 |
| 사냥 | 몬스터 (쓰러뜨리고 갈무리) | 대형 몬스터 사냥 · 갈무리 |
| 탐색 | 지도 (흔적 · 낯선 통로 · 서식지) | 조사 · 흔적 추적 |

다키스트 던전의 골동품(삽 · 열쇠 · 성수가 있어야 제대로 열림)이 몬헌의 채집 포인트에 대응한다. 채비 품목이 채집 지점을 여는 열쇠가 된다.

## 탐사 엔진: 구간마다 사건 하나

조우 규칙(조원마다 굴림 · 부상 주사위 · 포션 · 정비 도구 · 식량)은 그대로 쓴다.

| 사건 | 무엇 | 필요한 것 | 굴림 | 얻는 것 |
|---|---|---|---|---|
| 채집 지점 | 약초밭 · 광맥 · 결정 군락 | 채집 도구 | 조원마다 채집 굴림. 실패하면 낮은 확률로 조우로 넘어감 | 채집품 (짐 칸) |
| 조우 | 그 층 몬스터 (주 몬스터 · 곁 몬스터 둘) | 약점 장비 · 직업 | 지금 규칙 그대로 | 갈무리 소재 · 도감 기록 |
| 흔적 | 발자국 · 둥지 · 낯선 통로 | 지도 · 도적 · 길잡이 | 조원마다 굴림 (실패해도 위험은 낮음) | 지도 % · 새 채집 지점 · 노린 몬스터 위치 |

### 임무가 바꾸는 것

임무는 **출정 전에 조마다 하나** 정한다(행정관은 현장을 건드리지 않는다). 엔진에서 바꾸는 것은 아래 몇 가지로 제한한다.

- 사건 비중 (예시, 수치는 미정)

  | 임무 | 채집 지점 | 조우 | 흔적 |
  |---|---|---|---|
  | 채집 | 0.6 | 0.25 | 0.15 |
  | 사냥 | 0.15 | 0.5 | 0.35 |
  | 탐색 | 0.2 | 0.25 | 0.55 |

- 조우에서의 태도: 채집 임무는 물러서는 쪽(위험 ↓, 소재 ↓), 사냥 임무는 노린 몬스터에 맞서는 쪽.
- 먼저 바닥나는 채비: 채집 → 짐 칸, 사냥 → 포션 · 정비 도구, 탐색 → 횃불 · 식량.
- 배율: 채집품 · 소재 · 지도 증가량.

### 세 임무의 성격

| | 채집 | 사냥 | 탐색 |
|---|---|---|---|
| 지금 버는 것 | 많음 | 중간 | 거의 없음 |
| 나중에 버는 것 | 없음 | 도감 이해도 → 약점 확정 → 모든 조 성공률 | 지도 완성도 → 그 층 모든 조의 성공 · 안전, 채집 지점 증가 |
| 위험 | 낮음 | 높음 | 중간 |
| 어울리는 조 | 전사 둘(짐 +1칸) | 약점 장비 · 직업, 마법사 둘 | 도적 · 궁수, 길잡이 특성 |
| 귀환 보고의 초점 | 짐 · 시세 | 도감 기록 · 소재 | 지도 % · 발견 |

### 임무끼리의 연결

- **탐색이 지도를 넓히면 → 채집 지점이 늘고, 사냥은 흔적을 빨리 따라간다.** 지도가 잘 그려진 층일수록 사냥 조가 적은 구간 안에 노린 몬스터에 닿는다.
- 지도는 지금처럼 용병단의 자산이라, 탐색 조가 만든 가치는 사람이 떠나도 남는다.

## 시간 단위

- 층마다 시간 비용(본부를 비우는 날)과 현장 구간 수를 따로 둔다(지금 코드가 이미 그렇다: 위 "지금 코드와 맞춰 읽기"). 둘을 같은 숫자로 묶으면 결과가 동전 던지기가 되고 읽을 이야기와 채비의 의미가 사라진다.
- **1층은 짐이 차면 돌아오는 짧은 출근 층.** 횃불은 깊은 층에서 길이를 정하는 자원으로 둔다.
- 깊은 층에서 더 오래 머물게 하려면 구간을 늘리는 대신 **시간 비용을 한 날 늘리는** 식으로 연결한다("짐을 더 싣는 대신 하루 더 비운다").
- 채집품을 넣을 때 **한 달 기준 1층 벌이를 예전과 비슷하게** 맞춘다(1층 쏠림 재발 방지).

## 시장

지금의 두 갈래(전리품 / 갈무리 소재)를 임무에 맞게 다시 나눈다.

| | 채집품 | 사냥 소재 |
|---|---|---|
| 나오는 곳 | 채집 지점 | 조우에서 이긴 뒤 갈무리 |
| 양 | 많음 | 적음 |
| 값 | 싸고 안정적 (마을 살림에 늘 쓰임) | 비싸고 크게 출렁임 |
| 세금 | 처음부터 시장에 등록 | 많이 팔리면 영주청이 등록(법령), 그 전엔 세금 없음 |
| 성격 | 꾸준한 벌이 | 한 방, 그리고 도감 |

- 지금의 전리품(가죽 · 점액 · 마석 · 정령 결정 · 고대 유물 · 심층의 핵)을 채집품과 사냥 소재 중 어디에 둘지 정해야 한다. 이름으로 보면 가죽 · 점액은 사냥, 마석 · 정령 결정은 채집(광맥 · 결정 군락)에 가깝다. 시세 규칙(기본 가치 × `marketMul`, 층마다 물량 민감도 · 바닥 · 천장)은 그대로 쓴다.
- 나중의 확장거리: 약초 같은 채집품을 상단 포션의 재료로 엮어 약초 흉년(`potShock()`)과 잇는다. 범위가 커지니 이번에는 하지 않는다.

같은 역할을 하는 장치가 둘씩 생기지 않게, 기존 기능을 임무로 흡수한다.

| 기존 | 위치 | 어떻게 |
|---|---|---|
| 정찰 조 | `Team.scout`, `CO.SCOUT_MAP` · `SCOUT_CRISIS` · `SCOUT_LOOT` (기록실 2단계부터, 둘 · 셋만) | 탐색 임무로 흡수. 기록실 단계는 탐색 임무의 배율로 남긴다 |

| 싸움에서 나오는 전리품 | `Day.loot`, `CO.LOOT_SLOT` · `FIND` | 채집 지점의 채집품으로 옮긴다. 진 마주침에도 조금 싣는 규칙(`LOSE_LOOT`)은 채집 지점에 맞게 다시 정한다 |

| 찾는 곳 | `company.ts`의 찾는 곳 (소재를 더 쳐주는 곳) | 채집 지점 · 서식지 표시와 이을지 검토 |

## 데이터 모양 (안)

- `Team.mission: 'gather' | 'hunt' | 'scout'` (비워 두면 채집). `scout` · `target`은 `mission`으로 대신하고, 사냥 임무의 노릴 몬스터는 `target`을 그대로 쓴다.
- `Day.mon` → `Day.ev`: `{ k: 'gather' | 'fight' | 'trail', mon?: string, ... }`. 조우일 때만 `mon`을 채운다. 귀환 연출(`reveal.ts`)과 재생 장면(`scene.ts`)이 읽는 `Day.ms` · `Trip.dm`은 그대로.
- `TripCfg.evs`: 사건과 무게 (1단계에서 들어감). 사건별 굴림 함수는 `runMonth`가 넘겨 준다. `expedition.ts`는 지금처럼 굴리기만 한다.
- 저장 데이터 모양이 바뀌면 `src/coMain.ts`의 `VERSION`을 올린다.

## 화면

- **편성표:** 조 요약 줄에 임무 칸 하나. 사냥이면 노릴 몬스터 칸이 따라 나온다.
- **출정 층 선택 표 · 편성표:** 나중에 오는 이득을 지금의 숫자로 보인다. 예: "지도 +12% → 다음 달부터 이 층 조당 +40G 어림". `forecast()`가 난수 없이 셈하니 계산할 수 있다. 이게 없으면 탐색 · 사냥이 채집에 밀린다.
- **귀환 결과 날 칸:** 사건 종류로 색을 나눈다(예: 채집 초록 · 조우 빨강 · 흔적 파랑). 승 · 패 · 위기 · 사망 표시는 칸 안의 기호로.
- **귀환 보고:** 임무마다 초점 하나를 크게(채집: 짐 막대 · 판 값 / 사냥: 도감 기록 · 소재 / 탐색: 지도 % · 발견).
- **도감:** 지금처럼 기록만 보여 준다. 약점을 "~인 듯"으로 알려 주지 않는다.

## 경쟁 용병단

- 명단 없이 숫자로 굴리는 지금 방식을 유지하고, 성향마다 임무 비율을 둔다(예: 물량형은 거의 채집, 깊은 층 성향은 탐색 비중 높게).
- 정보망 단계에 따라 상대의 임무 비율이 보인다("철모회가 3층 지도를 그리고 있다" → 곧 3층에 몰려올 신호).

## 시뮬레이션으로 확인할 것

- 숙련 봇이 세 임무를 **골고루** 쓰는지, **시기에 따라** 비율이 바뀌는지(예: 초반 탐색 → 중반 사냥 → 후반 채집). 한 임무가 80~90%를 차지하면 가치를 다시 맞춘다(계약 조가 92% 달에 쓰여 "그냥 너무 좋은" 상태였던 것과 같은 문제).
- 모두 채집만 하는 봇과 비교해, 임무를 잘 고르면 이기는지.
- 1층 쏠림(1층 수입이 커져 1층 물량 용병단이 1위를 쓸어 가는 것)이 다시 생기지 않는지.
- 숙련 봇(`smart`)이 다른 봇보다 앞서는지. 밸런스를 바꾸면 전후 평균 순위와 1위 분포를 PR 설명에 적는다.

## 진행 순서

1. **엔진 일반화 (결과 그대로):** 구간마다 사건을 뽑는 구조로 바꾸되, 사건을 조우만 두어 지금과 같은 결과가 나오게 한다. 기존 테스트 · 시뮬레이션 숫자가 그대로인지 확인한다.
2. **채집 지점 + 전리품 이전:** 채집 지점 사건과 채집품을 넣고, 전리품을 채집품 · 사냥 소재로 나눈다. 시장 수치를 다시 맞춘다.
3. **흔적 + 탐색 임무:** 흔적 사건과 탐색 임무를 넣고, 정찰 조를 흡수한다.
4. **사냥 임무:** 지정 탐사를 흡수하고, 흔적 → 노린 몬스터 도달을 잇는다.
5. **화면과 경쟁 용병단:** 편성표 임무 칸, 날 칸 색, 귀환 보고 초점, 미래 이득 어림, 경쟁자 임무 비율.

각 단계마다 `npm run typecheck && npm test && npm run build`와 `npm run sim`.

## 열린 질문

- 임무는 조마다 하나로 고정할지, 비율(예: 채집 70 · 탐색 30)로 둘지. 하나가 단순하고 읽기 쉽다.
- 채집 지점에서 실패했을 때 조우로 넘어갈 확률.
- 사냥 임무가 노린 몬스터에 "닿았다"를 어떻게 판정할지(흔적 몇 번, 지도 %에 따라).
- 층마다 채집품 종류를 몇 개로 둘지.
- 지도 완성도가 채집 지점 비중을 얼마나 올릴지.
- 채집 도구를 용병단 전체 수준(`P.tool`)으로 둘지, 조마다 짐 칸을 쓰는 채비로 둘지.

## 지켜야 할 원칙 (CLAUDE.md에서)

- 결정은 숫자 · 정해진 칸으로. 대사 선택지는 없다. 행정관은 현장을 건드리지 않는다(임무는 출정 전 지시).
- 도감은 기록만 보여 준다. 짐작은 플레이어가 한다.
- 난수는 `core/rng.ts`의 `rnd()`만. 기록을 읽어 보여 주기만 하는 기능은 상태와 난수를 건드리지 않는다.
- `core`는 `ui`를 import하지 않는다. 몬스터를 더하거나 고칠 때는 `monsters.ts`만.
